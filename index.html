M.V. Masangkay Clinic

Online Appointment & Queue Management System

Technical Documentation & Thesis Presentation Script

Prepared by: Shenhelle Ashley Guantes  |  2026



System Purpose: A web-based clinic management system that allows patients to book appointments online with OTP verification, and provides clinic staff with a real-time queue control dashboard, SMS notifications, patient records, and analytics.

1. Complete System Flow

1.1 Patient Booking Flow

Step 1 — Mobile & OTP: Patient enters 10-digit mobile → OTP sent via SkySMS → Patient enters 6-digit code → Server validates via session.
Step 2 — Profile: System checks if mobile exists in DB. Existing patients see their saved profiles. New patients fill in the form.
Step 3 — Medical History: Patient fills symptoms, conditions, hereditary diseases, lifestyle info. Saved as JSON.
Step 4 — Services & Date: Patient selects lab tests. Picks appointment date — Sundays and PH holidays are blocked.
Step 5 — Submission: Booking saved as pending. Patient sees pending screen. System polls every 8 seconds.
Step 6 — Approval: Admin approves → queue number assigned → SMS sent → patient screen automatically updates to show queue number.

1.2 Admin Queue Flow

Step 1: Admin sees Appointments tab badge showing pending count for the selected date. Future bookings are visible by navigating the date picker.
Step 2: Admin reviews medical history modal → Approves or Rejects → SMS sent automatically.
Step 3: On appointment day — Queue Control tab shows waiting list (priority patients first).
Step 4: Admin clicks Call Next → previous patient marked done → next patient set to in_progress → SMS sent.
Step 5: Absent patients can be skipped and reinserted. Priority patients can be moved to the front.
Step 6 — End of Day (5 PM): Any remaining skipped appointments are auto-marked as disregarded.

2. Queue Logic & Detailed Example

2.1 How the Queue Works

Call Next

  1. If a patient is currently Now Serving (in_progress) → marks them as done.
  2. Fetches the next patient from confirmed status for today using this ORDER BY: 
    ORDER BY
  CASE WHEN priority_flags IS NOT NULL AND priority_flags != '' THEN 0 ELSE 1 END,
  created_at ASC
    Priority patients (Senior, Pregnant, PWD) always go first. Within each group, earliest booking time (FIFO).
  3. Sets that patient to in_progress → sends SMS notification.

Skip

  1. If a patient is Now Serving → moves them from in_progress to skipped.
  2. If no one is being served → moves the target appointment from confirmed or in_progress to skipped.
  3. Skipped patients appear in the Skipped section and can be reinserted.
  4. At 5:00 PM — all remaining skipped appointments are auto-marked disregarded.

Reinsert (from Skipped back to Queue)

  1. Changes patient status from skipped back to confirmed.
  2. Patient returns to the waiting queue at their original booking time position (natural FIFO — not moved to front).
  3. If they have a priority flag, they go before non-priority patients as normal.

Priority Insert (Move to Front)

  1. Sets the patient's created_at to TODAY 00:00:01.
  2. Since the queue orders by created_at ASC, this pushes them to the front of their group.
  3. If the patient has no priority flag, they go to the front of the regular (non-flagged) group — still behind any flagged patients.

4. Key Features & Automated Processes

3.1 7 AM Queue Reminder — sms-cron.php

Purpose: A scheduled cron job that runs every morning at 7:00 AM before the clinic opens. It automatically sends a reminder SMS to the top 5 patients in today's confirmed queue.
  • Queries appointments with status IN ('confirmed', 'in_progress') and DATE(preferred_date) = today.
  • Orders by queue number and takes the first 5 records (LIMIT 5).
  • Sends reminder SMS in Filipino to each patient.
  • Results logged in sms_logs with sms_type = 'called'.

Cron URL: https://mvmasankayclinic.xo.je/admin/sms-cron.php

Schedule: Hour 23 UTC = 7 AM PH time (UTC+8)

3.2 5 PM Auto-Disregard

Purpose: At 5:00 PM, the system automatically marks all skipped appointments as disregarded, closing out the day's queue cleanly.
  • Triggered on every admin dashboard page load after 5:00 PM.
  • Checks: if (intval(date('H')) >= 17)
  • Only affects today's skipped appointments — does not touch future dates.

3.3 Real-Time Status Polling — 8-Second Interval

Purpose: After booking, the patient portal checks for status updates every 8 seconds. When approved, the screen updates automatically without page refresh.
  • startStatusPolling(appointment_id) calls check-appointment-status.php every 8 seconds.
  • On confirmed: displays queue number, people ahead, and estimated wait time.
  • On rejected: shows rejection screen.
  • Queue state saved in localStorage — survives page refresh.
  • Estimated wait = people_ahead × 5 minutes.

3.4 Priority Queue System (Senior / Pregnant / PWD)

Purpose: Priority patients are automatically placed ahead of regular patients regardless of booking time.
  • Patient selects priority pills during booking: Senior Citizen, Pregnant, PWD.
  • Stored in appointments.priority_flags as comma-separated values.
  • Queue order: Priority patients first → then FIFO by created_at.
ORDER BY
  CASE WHEN priority_flags IS NOT NULL AND priority_flags != '' THEN 0 ELSE 1 END,
  created_at ASC

3.5 OTP Reuse Within 5-Minute Window

Purpose: If a patient requests OTP resend within 5 minutes, the same code is resent instead of generating a new one — preventing patient confusion.
  • If valid OTP exists in session for same mobile → resend same code, expiry unchanged.
  • If expired or different mobile → generate new code, reset 5-minute timer.
  • OTP not cleared after verification — valid until natural expiry.

3.6 Holiday & Sunday Blocking

Purpose: Prevents bookings and admin navigation on non-operating days.
  • Patient portal: validateAppointmentDate() blocks Sundays and PH holidays — clears input and shows error toast.
  • Admin dashboard: adminDateSafe(input, callback) applied to all 3 date filters (Appointments, Patients, Analytics).
  • Covers fixed holidays (New Year, Labor Day, Christmas, etc.) and moveable holidays (Holy Week, Eid, National Heroes Day) for 2025–2026.

3.7 Mobile Number Auto-Formatting

  • Strips non-digit characters on input.
  • Removes leading 0 or 63 prefix automatically.
  • Formats as 9XX XXX XXXX with spaces.
  • Validates: exactly 10 digits starting with 9.

3.8 Patient Data CSV Export

  • Reads patient rows from the live DOM table — no server request needed.
  • Mobile formatted as +63XXXXXXXXX with tab prefix to prevent Excel scientific notation.
  • UTF-8 BOM included for correct Filipino character rendering in Excel.
  • Downloaded as: patients_YYYY-MM-DD.csv

3.9 Queue State Persistence (localStorage)

  • saveQueueToStorage(appointment_id) saves ID and mobile after booking.
  • restoreQueueState() on page load checks localStorage and restores screen.
  • If approved: queue number and people-ahead count restored automatically.
  • If rejected: rejection screen shown.

5. Possible Panel Questions & Answers

Note: Practice these answers aloud before the defense. Keep answers under 1 minute each.

Q: Why did you choose PHP instead of a modern framework like Laravel or Node.js?

"PHP was chosen because it is the most widely supported language on shared hosting platforms like InfinityFree, which our clinic uses for deployment. It requires no additional setup, runs on any standard web server with XAMPP locally, and the team has direct experience with it. For the scope of this system — a single-clinic appointment and queue management tool — vanilla PHP with prepared statements provides everything we need without the overhead of a full framework."

Q: Why SkySMS instead of Twilio?

"We initially configured Twilio but discovered that US local numbers cannot send SMS to Philippine (+63) numbers without a multi-week carrier registration process. SkySMS is a Philippine-built SMS gateway specifically designed for local mobile numbers, making it the most practical solution. It also has lower per-SMS costs for Philippine numbers compared to international gateways."

Q: How secure is the OTP system?

"The OTP is generated using PHP's cryptographically secure random_int() function and stored server-side in the PHP session — never exposed to the client browser. It expires after 5 minutes. Verification uses hash_equals() for constant-time comparison to prevent timing attacks. The patient's mobile number must also match the session for verification to succeed, preventing replay attacks."

Q: What happens if the internet is unavailable during clinic operations?

"If the system is run locally on XAMPP within the clinic's local area network, it operates fully without external internet. Queue management, appointment approval, and patient records all function on the local network. Only SMS notifications and the live website would be unavailable — but the admin dashboard would still be accessible from within the clinic."

Q: Can the system handle multiple concurrent bookings?

"Yes. Queue number assignment uses a COUNT query per date and assigns the next sequential number atomically. All queries use prepared statements which ensure data integrity under concurrent requests. PHP sessions are completely isolated per user, so simultaneous bookings from different patients do not interfere with each other."

Q: What are the system's limitations?

"The main current limitations are: first, patients can select a date but not a specific time slot — all appointments for a given day compete in one queue. Second, the SMS gateway requires a paid subscription for API access beyond the free tier. Third, the system supports only a single clinic branch. Fourth, the admin queue requires a manual page refresh to update — it does not auto-refresh. These are all identified areas for future development."

Q: How does the priority queue system comply with Philippine law?

"Republic Act 9994 (Expanded Senior Citizens Act), RA 11861 (Expanded Solo Parents Act), and RA 7277 (Magna Carta for Disabled Persons) all mandate priority service for senior citizens, pregnant women, and PWDs in public establishments. Our system implements this through priority flags that automatically place these patients at the front of the queue, ensuring legal compliance and equitable healthcare access."

Q: How do you ensure data privacy under the Data Privacy Act of 2012 (RA 10173)?

"Patient data is protected through several mechanisms: all database queries use prepared statements to prevent unauthorized access, admin access is protected by session-based authentication with bcrypt-hashed passwords, the OTP system verifies patient identity before any data is shown, and sensitive credentials are stored in a git-ignored config file that is never committed to version control. The system collects only the minimum data needed for clinic operations."

Q: Why does the system collect medical history if this is just a queue system?

"The medical history collection serves two purposes. First, it allows the admin to make informed decisions when approving or rejecting appointments — for example, a patient with certain conditions may need to be seen earlier or referred elsewhere. Second, it reduces the time spent on intake forms at the clinic counter. The medical history is stored as structured JSON and is viewable only by authenticated admin staff."

Q: What is the difference between the preferred_date and created_at fields?

"created_at is when the patient submitted the booking — this is the booking timestamp. preferred_date is the actual appointment date the patient selected — when they want to visit the clinic. These can be different days. For example, a patient might book on June 1 for an appointment on June 5. The queue system operates on preferred_date so the clinic sees the correct patients each day."

Q: How does the system prevent fake or duplicate bookings?

"Every booking requires OTP verification through the patient's registered mobile number — this confirms the patient's identity before any booking is accepted. If a patient submits duplicate bookings, they all appear in the admin Appointments tab for review before approval. The admin reviews the medical history before approving, providing a human checkpoint for unusual or duplicate requests."

Q: What happens if the admin does not approve a booking before the appointment date?

"The appointment remains in pending status. On the patient's side, the booking screen continues to show 'Pending Review.' The patient will not receive a queue number and cannot join the queue until approved. The admin Appointments tab shows all pending bookings for any date, including past dates, so the admin can still approve or reject them after the fact."

Q: How scalable is the system if the clinic grows?

"For a single-branch clinic of this scale, the current architecture is sufficient. For larger scale, the identified improvements include: time slot selection to distribute patients across the day, multi-branch support with a branch_id column, and upgrading to a more robust hosting plan with dedicated resources. The use of prepared statements and indexed database queries ensures the system maintains performance even as patient records grow."

Q: How did you test the system?

"The system was tested through functional testing of each booking step, admin workflow testing covering appointment approval, queue operations, and SMS sending. We also tested edge cases such as expired OTPs, duplicate mobile numbers, priority patient ordering, and the 5 PM auto-disregard feature. The live deployment at mvmasankayclinic.xo.je was used for end-to-end testing with real SMS delivery."

Q: Why is the patient portal a single-page application instead of multiple pages?

"A single-page architecture was chosen to provide a smooth, app-like booking experience. Navigating between steps does not reload the page, which means patient data entered in earlier steps is preserved in JavaScript memory. It also reduces server load since only specific API calls are made at each step rather than full page reloads. The browser Back button is supported through the HTML5 History API so the experience feels natural."

Q: What is the role of the medical history in the approval process?

"The admin reviews the patient's medical history — including symptoms, chronic conditions, hereditary diseases, past surgeries, allergies, smoking and drinking habits — before approving or rejecting the appointment. This allows the clinic to prioritize urgent cases, identify patients who may need referral, and prepare the appropriate staff or equipment before the patient arrives. Review notes can also be added and are visible to the patient."

Q: What happens to a skipped patient if they arrive after being skipped?

"The admin can click the Reinsert button on the skipped patient in the Queue Control tab. This changes their status back to confirmed and places them back in the waiting queue at their original booking time position. If they have a priority flag (senior, pregnant, PWD), they will still be placed ahead of regular patients. If they are not reinserted by 5:00 PM, the system automatically marks them as disregarded to keep the queue data clean."

Q: How does the system ensure the queue is in the correct order?

"The queue order is determined by two criteria. First, priority patients — those flagged as senior citizen, pregnant, or PWD — are always placed before regular patients regardless of booking time. Second, within each group (priority and regular), patients are ordered by the time they booked (created_at ASC) — this is first come, first served. The Priority Insert feature allows the admin to manually push a confirmed patient to the front of their group by setting their created_at to the start of today."

Q: What if two priority patients book at the same time — who goes first?

"If two priority patients have the same created_at timestamp (which is extremely rare but possible), MySQL's natural row order would determine who goes first. In practice, since bookings come in through a web form, the created_at values are unique to the millisecond in most cases. If truly simultaneous, the admin can use Priority Insert to manually set the order."

Q: Why is the queue filtered by preferred_date instead of created_at?

"The queue is built around the day the patient wants to visit the clinic, not the day they booked. A patient might book three days in advance for a Tuesday appointment — their created_at would be Saturday but their preferred_date is Tuesday. The queue control must show Tuesday's patients on Tuesday, not Saturday's patients. Using preferred_date ensures the correct patients appear in the queue each day regardless of when they submitted their booking."

Q: What happens if the admin does not click Call Next at the end of the day?

"Any patients still in in_progress status from a previous day will be excluded from the current day's queue because getCurrentServing() filters by DATE(preferred_date) = today. To clean up stale in_progress appointments, the admin can run a manual SQL query in phpMyAdmin: UPDATE appointments SET status='confirmed' WHERE status='in_progress' AND DATE(preferred_date) < CURDATE(). The system does not auto-close in_progress appointments, only skipped ones."

Q: How does the SMS notification work when a patient is called?

"When the admin clicks Call Next, the system fetches the next confirmed patient, sets them to in_progress, and immediately calls the logSMS() function with the sms_template_called template. The message is customizable from the admin settings and supports [Patient Name] and [Queue #] placeholders. The SMS is sent via the SkySMS API and the result is logged in the sms_logs table whether it succeeded or failed. This gives the admin a full audit trail of all notifications sent."

Q: How do you handle the case where a patient books for a Sunday or a holiday?

"The patient portal's date picker uses a JavaScript validation function that checks if the selected date is a Sunday using date.getDay() === 0, and checks against a pre-defined set of Philippine public holidays including fixed holidays like New Year, Labor Day, Christmas, and moveable ones like Holy Week and Eid. If the patient selects a blocked date, the field is cleared and an error toast is shown. The admin dashboard's date filters also use the same blocking logic to prevent navigating to non-operating days."

Q: Why does the system store medical history as JSON instead of separate database columns?

"Medical history has a variable structure — different patients may have different combinations of symptoms, conditions, and lifestyle factors. Storing it as JSON in a MEDIUMTEXT column avoids creating dozens of nullable columns in the appointments table. The JSON is decoded in PHP when displaying the medical history modal in the admin dashboard. This approach is flexible and allows future fields to be added without altering the database schema."

8. Code Documentation — Important Blocks

7.1 db.php — Database Connection

Purpose: Establishes MySQL connection and sets Philippine timezone. Included by all PHP files needing the database.
  • date_default_timezone_set('Asia/Manila') — ensures all PHP date functions use Philippine Standard Time (UTC+8). Critical for InfinityFree hosting which defaults to UTC.
  • db_query(sql, types, params) — prepared statement wrapper preventing SQL injection.
  • db_row(sql, types, params) — fetches a single row using a prepared statement.
  • db_insert_id() — returns last auto-increment ID after an INSERT.

7.2 includes/sms.php — SMS Functions

Purpose: All SMS sending logic. Used by send-otp.php, appointment-action.php, queue-action.php, and send-manual-sms.php.

sendSMS(string $mobile, string $message): array

Formats the mobile to E.164 (+63XXXXXXXXXX) and calls the SkySMS REST API via cURL.

Number normalization:

  • 10 digits (9XXXXXXXXX) → prepend 63 → +639XXXXXXXXX
  • 11 digits starting with 0 → replace leading 0 with 63 → +639XXXXXXXXX
  • No + prefix → prepend + → +639XXXXXXXXX

generateAndSendOTP(string $mobile): bool

Generates a 6-digit OTP stored in PHP session with 5-minute expiry. If a valid OTP already exists for the same mobile within 5 minutes, the same code is reused — preventing confusion when the patient clicks Resend.

verifyOTP(string $mobile, string $submitted): bool

Validates the submitted code against the session-stored OTP. Uses hash_equals() for constant-time comparison. OTP is NOT cleared after verification — valid until natural expiry.

7.4 submit-appointment.php

Purpose: Saves the booking. Creates or updates patient record, then inserts appointment as pending.
  • If mobile exists in patients → UPDATE profile (not duplicate)
  • If new → INSERT patient, get new ID
  • Priority flags validated against allowlist (senior, pregnant, pwd)
  • Medical history serialized to JSON
  • Returns appointment_id for frontend polling

7.5 admin/appointment-action.php — Approval Logic

Purpose: Approve, reject, or cancel appointments from the admin panel.

Approve: Counts existing queue numbers for the same preferred_date. Assigns next sequential number (001, 002…). Updates status to confirmed. Sends approval SMS.

Reject: Updates status to rejected. Sends rejection SMS.

Cancel: Updates status to cancelled (no SMS).

7.6 admin/queue-action.php — Queue Operations

Purpose: Real-time queue management. All queries filter by DATE(preferred_date) = today to prevent stale data from other days.
ActionWhat It Does
callMarks current in_progress as done → gets next confirmed (priority first, then FIFO) → sets to in_progress → sends SMS
doneMarks current in_progress as done without calling next patient
skipMoves current or selected confirmed patient to skipped
reinsertMoves a skipped patient back to confirmed (back into queue)
priority_insertMoves a patient to front of queue by setting created_at to 00:00:01 today

11.3 SMS Logs Tab Shows No Data on Live Site

Symptoms: SMS Logs tab is empty on the live site but works on localhost. Sent/failed counts all show 0.

Cause: InfinityFree MySQL uses UTC. PHP date() now returns PH date but MySQL's DATE(created_at) still evaluates in UTC, causing a date mismatch.

Fix — Already Applied in db.php

$mysqli->query("SET time_zone = '+08:00'");

If the issue persists, verify the updated db.php is deployed to InfinityFree. Create test-time.php on server to verify:

<?php require_once 'db.php'; echo date('Y-m-d H:i:s'); // Should show PH time

11.4 Queue Shows Wrong / Stale "Now Serving" Patient

Symptoms: A patient from a previous day still appears as Now Serving. Queue does not progress.

Cause: An appointment was left in in_progress status when the admin closed the browser without marking done.

Fix — Run in phpMyAdmin

UPDATE appointments SET status = 'done'
WHERE status = 'in_progress' AND DATE(preferred_date) < CURDATE();

11.5 Skip Button Does Not Show Patient in Skipped Table

Symptoms: Clicking Skip shows "Patient skipped" toast but the skipped table does not appear after reload.

Cause: PHP's getCurrentServing() filters by DATE(preferred_date) = today. If this returns null (timezone edge case on live server), the fallback UPDATE only targeted status='confirmed' — missing the in_progress patient.

Fix — Already Applied in queue-action.php

UPDATE appointments SET status='skipped'
WHERE id=? AND status IN ('confirmed','in_progress')

Also ensure the MySQL timezone is set to PH time (see 11.3).

11.6 Multiple People Using Same Mobile — Only Last Person Shows in Profile List

Symptoms: Two family members book using the same number. Only the latest person's name appears in the existing profile selection.

Cause: submit-appointment.php was doing SELECT id FROM patients WHERE mobile=? LIMIT 1 and overwriting that record with whoever just booked.

Fix — Already Applied

  • patient.js — now sends patient_id when an existing profile is selected.
  • submit-appointment.php — if patient_id is provided, updates only that specific record. If patient_id = 0 (new profile), always inserts a new patient record instead of overwriting.
